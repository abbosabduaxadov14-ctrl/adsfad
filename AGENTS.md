## Order of work

1. Understand the requested outcome and inspect the existing implementation. Reuse known decisions instead of asking the user to repeat them. Identify the actual problem before selecting tools.
2. Define a short, observable completion checklist before a substantial change. State assumptions and identify answers that would materially change the product. Make routine decisions independently.
3. Plan the smallest complete student journey. Sequence dependencies: source/course -> lecture -> activity -> reflection -> pathways. Distinguish confirmed course material from Hamkema draft exercises.
4. For substantial visual changes, make one representative working page available early for feedback. Continue independent work while feedback is pending; do not assume silence approves a consequential design choice.
5. Implement in coherent, reviewable increments. Complete the main journey before adding supporting features. Preserve working behavior and user work. Keep a recoverable checkpoint before broad changes, using existing version history or a scoped local backup where appropriate; never overwrite user changes.
6. Verify behavior and appearance. Use relevant existing checks, inspect the running site, and exercise the affected journey on desktop and mobile. Check keyboard access, media fallbacks, empty/error states, and persistence where affected. Fix discovered problems and recheck affected behavior. A passing script alone does not establish visual quality.
7. Compare the result with the original completion checklist. Report what was built, what was actually tested, and what remains pending. If browser inspection or a service connection is unavailable, name the unverified part explicitly.
8. Keep PROJECT.md current when project decisions or next steps change. Turn repeated, observed mistakes into specific guidance; do not turn one-off preferences into universal rules.
